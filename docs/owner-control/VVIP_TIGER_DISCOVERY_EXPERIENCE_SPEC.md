## دور الاكتشاف داخل NEXUS

الاكتشاف والبحث **وحدة داخل TIGER NEXUS 2026** وليسا منتج Marketplace موازيًا.

الاكتشاف يعرض ويبحث ويرشح **نفس Living Sector Object** الموجود في الـFeed والملف الشخصي والأسطح الأخرى. لا ينشئ كائن إعلان ثانٍ، ولا Composer ثانيًا، ولا مسار نشر مستقلًا.

كل كائن منشور حاليًا يرتبط بقطاع مفعّل وIntent من:

- `OFFER`
- `NEED`
- `SERVICE`
- `OPPORTUNITY`

القطاعات لا تُثبت بعدد أو قائمة جامدة داخل هذه المواصفة. مصدر القطاعات الحالي هو الـserver-authoritative **activated sector registry**.

## مبادئ تجربة البحث

نحافظ على تجربة مألوفة وسهلة دون نسخ علامة أو هوية أي منصة أخرى:

- App Shell سريع وواضح.
- Search ظاهر وسهل الوصول.
- بحث بسيط أولًا، وخيارات إضافية عند الحاجة.
- انتقال سهل بين القطاعات المفعلة.
- Feed وبطاقات متسقة مع NEXUS.
- استجابة جيدة للهاتف والشاشات الضعيفة.
- Loading / Empty / Error / Retry حالات حقيقية.
- لا زر ميت ولا نتيجة وهمية.
- لا تحميل لكل النتائج دفعة واحدة عند ازدياد البيانات.

## الفلاتر الحالية

الفلاتر الأساسية يمكن أن تشمل، عندما تكون البيانات الحالية والقطاع المفعّل يدعمانها:

- القطاع المفعّل؛
- كلمة البحث؛
- النطاق الجغرافي المدعوم؛
- Intent؛
- خصائص القطاع المنظمة التي يعيدها العقد الحالي؛
- الترتيب أو الفرز المدعوم فعليًا.

أي خصائص إضافية مثل السعر أو الحالة أو الماركة أو نوع العقار أو غيرها تكون **sector-schema driven** عند وجودها في عقد القطاع الحالي، وليست قائمة ثابتة مفروضة من هذه الوثيقة.

## مصدر البيانات الحالي

التنفيذ الحالي للاكتشاف هو:

`scripts/nexus/sector-discovery.js`

ويقرأ Living Sector Objects من Social Runtime / Social Feed read model، ثم يفلترها باستخدام القطاع والبحث الحاليين.

مصدر القطاعات المسموح بعرضها هو registry المفعّل حاليًا، وليس قائمة ثابتة داخل الواجهة.

لا يُستخدم `window.VVIPDiscovery.setItems(...)` كسلطة runtime حالية، ولا يجوز إعادته كمسار موازٍ.

## حدود الصلاحية

واجهة البحث لا تمنح:

- صلاحية نشر؛
- صلاحية إدارية؛
- تجاوزًا للخصوصية أو RLS؛
- تجاوزًا لأهلية القطاع/Intent؛
- تجاوزًا لقواعد الحظر أو السلامة؛
- تجاوزًا لقواعد Pulse؛
- صلاحية دفع أو تعامل مالي بين أطراف السوق.

النتائج يجب أن تأتي من إسقاطات آمنة ومسموح بها من الخادم.

## الأداء

عند الحاجة ووفق التنفيذ الفعلي يمكن استخدام:

- Debounce؛
- pagination أو progressive loading؛
- caching آمن للبيانات غير الحساسة؛
- Skeleton؛
- bounded retry؛
- منع الطلبات المكررة؛
- عدم إعادة بناء الصفحة كاملة دون حاجة؛
- degraded behavior واضح عند ضعف الاتصال.

لا تتحول أي تقنية أداء إلى مصدر بيانات أو صلاحية مستقلة.

## العلاقة مع Pulse

Pulse اختياري ويخص الظهور المدفوع للكائن نفسه بعد الأهلية. البحث والاكتشاف لا ينشئان كائنًا مدفوعًا منفصلًا.

الترتيب أو الظهور المدفوع، عندما يطبق، يبقى server-authoritative ولا يتجاوز الأهلية أو السلامة أو السياسة أو الصلة أو حدود الاستهداف المعتمدة.
