# TIGER NEXUS 2026 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the first production-quality TIGER NEXUS slice: social-first shell, sector-intent creation, real capability passport, Pulse Vault/non-expiring visibility, and verified-delivery controls while deleting conflicting current-tree behavior.

**Architecture:** Extend the current single social surface rather than creating a second application. Introduce small bounded contracts/read models for NEXUS intent, capability passport, and Pulse Vault, then wire them into the existing shell. Preserve server-authoritative authorization and Pulse verification; client UI only renders validated state. Conflicting legacy/current-tree paths are identified and deleted rather than hidden or retained as fallback.

**Tech Stack:** Static HTML/CSS/JavaScript, Node.js test runner scripts already present in the repository, Supabase/RPC-backed server-authoritative runtime adapters, GitHub Actions quality gates.

**Spec:** `docs/superpowers/specs/2026-08-29-tiger-nexus-2026-design.md`

## Global Constraints

- Primary product surface is `SOCIAL_NETWORK_FIRST`; Marketplace remains a module, not the default home.
- Independent TIGER identity; do not copy Facebook branding, logos, exact protected layouts, or wording.
- General-purpose non-sector chatter is not publishable in the NEXUS content contract.
- Ordinary eligible sector publication remains free; Pulse is optional paid visibility.
- Current Pulse reference levels remain exactly 2 / 10 / 25 / 45 JOD.
- Purchased Pulse visibility has no product-time expiry.
- Pulse consumption remains server-authoritative and follows `RESERVE → SERVE → VERIFY → CONSUME`.
- `NOW`, `SMART`, `PRECISE` affect delivery strategy only, never purchased quantity or eligibility.
- `☰` is the persistent TIGER Command trigger; `صلاحياتي` renders real validated capability state.
- Frontend visibility is not authorization; server/RLS/capability enforcement remains authoritative.
- New owner-approved behavior supersedes conflicting old current-tree behavior.
- Conflicting old behavior is deleted from Runtime/UI/API/Config/Tests/CI/Current Docs/Launch Gates; no archive/trash/legacy/fallback/compatibility copy remains. Git history is the provenance mechanism.
- No direct writes to `main`; exact-head tests must pass before protected merge.
