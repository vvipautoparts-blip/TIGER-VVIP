# F10A Arabic/English i18n Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans with TDD. F10A builds one bilingual product contract; it does not fork the application by language.

**Goal:** Establish a single Arabic/English message catalog and locale formatter for FUSION with RTL/LTR direction, locale-aware numbers, dates, and currencies.

**Architecture:** A pure CommonJS core consumes one parity-checked catalog with `ar` and `en` messages under identical keys. Locale selection returns direction plus formatting helpers based on `Intl`. UI phases consume keys instead of duplicating business logic or pages.

**Files**
- Create: `scripts/fusion/i18n/messages.js`
- Create: `scripts/fusion/i18n/i18n-core.js`
- Create: `tests/f10a-i18n-core.test.cjs`
- Create: `docs/fusion/F10_I18N_CORE.md`

## Invariants
- Launch locales: `ar`, `en`.
- Arabic direction = `rtl`; English = `ltr`.
- Catalog key parity is mandatory.
- Unknown locale falls back to Arabic only through an explicit fallback result.
- Missing translation key returns a stable error result; it never silently shows a different business meaning.
- Number/date/currency formatting uses `Intl`, not manual string concatenation.
- Currency code is caller-provided ISO code; i18n does not invent FX rates.
- Core is pure: no browser storage, network, or environment secrets.

### TDD contract
Tests cover locale direction, Arabic/English key parity, known message lookup, missing-key behavior, number formatting, currency formatting, date formatting, and fallback locale behavior.

### Verification
Run focused `node:test`, then repository CI when an exact-head validation route is available. No Production deploy.
