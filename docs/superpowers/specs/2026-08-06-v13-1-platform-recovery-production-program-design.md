# برنامج استعادة TIGER VVIP وتوحيد V13.1 والجاهزية الإنتاجية

**التاريخ:** 2026-08-06  
**الحالة:** معتمد للتنفيذ بموجب تفويض المالك الكامل لاتخاذ القرارات التقنية والتنفيذية الآمنة  
**النطاق:** المستودع `vvipautoparts-blip/TIGER-VVIP`  
**مرجع البداية:** `main@4cc292e626fea39f3b0e56b98781d521efef789d`

## 1. الملخص التنفيذي

المنصة ليست مشروعًا فارغًا يحتاج إلى إعادة بناء كاملة، كما أنها ليست جاهزة للدمج العشوائي أو الإطلاق المباشر. المستودع يحتوي على واجهة Static Multi-Page عاملة، نظام تصميم قائم، تكاملات Clerk وSupabase وFirebase تاريخية، طبقات Project Control، اختبارات أمن وجودة، وسلسلة كبيرة من Pull Requests المتدرجة الخاصة بـV13.1.

المشكلة الأساسية هي **تشتت السلطة التقنية** بين وثائق وتشغيلات وفروع متعددة، وليس غياب العمل. العلاج المعتمد هو برنامج استعادة وتوحيد تدريجي يحافظ على الأجزاء المثبتة، يلغي التناقضات، ويُنشئ مسار إصدار واحدًا قابلًا للتدقيق والتراجع.

القرار النهائي هو اعتماد نهج **Consolidation-First Zero-Trust Release Train**:

1. احتواء المخاطر الأمنية والتنظيمية قبل أي توسع.
2. تثبيت مصدر حقيقة تنفيذي واحد.
3. تصنيف PRs والفروع واستخراج التغييرات المعتمدة فقط.
4. بناء Integration Train نظيف من `main` بدل دمج السلسلة المتراكمة دفعة واحدة.
5. إكمال المنتج على شرائح مستقلة قابلة للاختبار.
6. الانتقال عبر Local ثم Preview ثم Staging ثم Production Canary.
7. منع أي إجراء إنتاجي غير قابل للتراجع من دون دليل وRollback واختبارات على نفس SHA.

## 2. البدائل التي جرى تقييمها

### البديل A: إعادة البناء الكامل من الصفر

**المزايا:** حرية معمارية كاملة، هيكل ملفات نظيف نظريًا.  
**العيوب:** يهدر العمل المثبت، يعيد فتح أخطاء الدخول والملفات والصلاحيات، يطيل الوصول للإنتاج، ويزيد خطر فقدان سلوكيات الواجهة الحالية.  
**القرار:** مرفوض.

### البديل B: دمج جميع PRs الحالية حسب ترتيبها

**المزايا:** يبدو سريعًا ويحافظ على التسلسل التاريخي.  
**العيوب:** بعض PRs Verification-Only أو Never-Merge، وبعضها متدرج فوق قواعد مختلفة، وبعض الوثائق تصف معماريات متعارضة. الدمج الأعمى قد يمرر تعارضًا منطقيًا رغم نجاح الاختبارات المنفردة.  
**القرار:** مرفوض.

### البديل C: التوحيد التدريجي مع استخراج الشرائح المثبتة

**المزايا:** يحافظ على القيمة، يعزل المخاطر، يتيح مقارنة سلوكية قبل وبعد، ويعطي كل شريحة اختبارات وRollback مستقلين.  
**العيوب:** يحتاج جردًا وتصنيفًا دقيقًا قبل الدمج.  
**القرار:** **معتمد** لأنه الأقل مخاطرة والأعلى جودة على المدى الطويل.

## 3. المبادئ غير القابلة للتفاوض

1. **لا تخمين للإنتاج:** لا تُفعّل دولة أو دفع أو Migration بعيدة أو صلاحية مالك اعتمادًا على Fixtures أو افتراضات.
2. **Fail Closed:** غياب الهوية أو السياسة أو الاتصال أو الدليل أو التوقيع يُنتج رفضًا، لا نجاحًا محليًا مضللًا.
3. **Clerk هو سلطة الهوية الأساسية:** لا يجوز تشغيل سلطتي دخول متنافستين في المسار الأساسي.
4. **Supabase هو سلطة البيانات والتخزين:** الوصول المميز يمر عبر حدود خادمية موثوقة وسياسات RLS مراجعة.
5. **لا سلطة مميزة من المتصفح:** localStorage وحقول الطلب لا تمنح Role أو Country أو Owner أو Partner Authority.
6. **Static Multi-Page محفوظ حاليًا:** لا يُضاف Framework أو Bundler لمجرد الحداثة؛ أي انتقال تقني لاحق يحتاج فائدة قابلة للقياس وخطة ترحيل.
7. **أفضل أداة هي الأكثر ملاءمة لا الأحدث اسمًا:** التميز يُقاس بالأمان والسرعة وتجربة المستخدم وسهولة الصيانة، لا بكثرة المكتبات.
8. **TDD وExact-Head Evidence:** الاختبار الفاشل يسبق الإصلاح، وجميع بوابات القرار النهائي تعمل على SHA واحد.
9. **لا Merge مباشر إلى `main`:** كل تغيير عبر فرع معزول وPR ومراجعة وبوابات إلزامية.
10. **التراجع جزء من التصميم:** لا تُعد أي شريحة مكتملة من دون طريقة رجوع مثبتة.
11. **Arabic-First + English:** دعم RTL/LTR وتناسق المصطلحات ليس تحسينًا اختياريًا.
12. **WCAG 2.2 AA:** الوصولية شرط قبول للواجهات الجديدة والمعدلة.
13. **الخصوصية بالحد الأدنى:** لا تُخزن بيانات أو Payloads أو سجلات أكثر مما تتطلبه الوظيفة والتدقيق.
14. **لا أسرار داخل Git:** ملفات البيئة المحلية والمفاتيح الحقيقية لا تُتبع في المستودع.
15. **التنظيف الآمن لا الحذف الأعمى:** TIGER CleanGuard يعزل ويثبت قابلية الاستعادة قبل إزالة أي مخلفات.

## 4. الحالة المعمارية المستهدفة

```text
Browser / PWA
  -> Static canonical pages and focused JavaScript modules
  -> Clerk session boundary
  -> Server-trusted command/query boundary
  -> Authorization envelope + country scope + policy revision
  -> Supabase data/storage with FORCE RLS
  -> Append-only audit + idempotency receipts

External navigation
  -> WhatsApp deep link only
  -> No internal WhatsApp message ingestion or storage

Operations
  -> Owner/partner/admin console
  -> Server-derived authority
  -> Immutable audit trail
```

### 4.1 الواجهة

- `index.html` يبقى المدخل الموحد للسوق والدخول حتى اكتمال تقييم مستقل لأي إعادة هيكلة.
- `private-profile-p03.html` يبقى مركز الحساب الخاص المرجعي.
- الملفات المرجعية الحالية تحت `styles/` و`scripts/` تُراجع وتُجزأ فقط عندما يثبت أن حجم الملف أو تداخل المسؤوليات يعيق الاختبار والصيانة.
- Design Tokens موحدة للون والمسافة والطباعة والحركة والحدود والحالات.
- الواجهة Responsive من الهاتف أولًا، مع Navigation واضح وReduced Motion ودعم قارئات الشاشة.

### 4.2 الهوية والجلسة

- `auth-clerk-index.js` هو مسار الدخول المرجعي للواجهة الرئيسية.
- Firebase لا يبقى سلطة دخول منافسة. أي وظيفة تاريخية ما زالت تعتمد عليه، مثل Password Reset، تُصنف Compatibility Surface وتُرحّل أو تُعزل ضمن خطة مستقلة.
- لا تُقبل أدوار أو هوية من localStorage كسلطة؛ يمكن استخدامه فقط Snapshot غير حساس لتحسين العرض.

### 4.3 البيانات والتفويض

- جميع عمليات الكتابة المميزة تمر عبر Command Boundary خادمية.
- جميع عمليات القراءة الحساسة تمر عبر Query Boundary منفصلة.
- سياسات OWNER_ROOT وPARTNER_GLOBAL_ADMIN ونطاقات الدول والقطاعات تُطبق خادميًا وداخل RLS.
- Idempotency دلالية Versioned، وسجل التدقيق Append-Only.
- لا Migration بعيدة قبل نجاح reset محلي قابل للتكرار، مقارنة Ledger، نسخة احتياطية، وخطة Rollback.

### 4.4 الوسائط

- الحد الدستوري العالمي هو 7 صور للإعلان.
- الفيديو غير مفعّل في الإصدار الحالي.
- معالجة الصور تستخدم Validation ثنائي المرور: فحص أمني بنيوي ثم تصنيف أخطاء المجال.
- التخزين يعزل المسارات حسب المستخدم/الإعلان ويمنع Path Traversal وMIME Spoofing والملفات المتضخمة.
- Upload UX يعرض Progress وRetry وCancellation ورسالة خطأ مستقرة.

### 4.5 المراقبة والتشغيل

- Structured Logs بلا أسرار أو بيانات شخصية غير لازمة.
- Correlation IDs لجميع العمليات الخادمية.
- مؤشرات أساسية: خطأ الدخول، فشل الرفع، زمن البحث، فشل RLS، تعارض Idempotency، وفشل الدفع عند تفعيله.
- Feature Flags، Kill Switch، Canary، وRollback Release Artifact.

### 4.6 TIGER CleanGuard — برنامج حذف الزبالة والتنظيف الآمن

TIGER CleanGuard هو نظام Repository/Data Hygiene وليس أمر حذف شامل. يعمل بخمس مراحل إلزامية:

1. **Discover:** اكتشاف الكود الميت، الملفات المكررة، Build Artifacts، Caches، الوثائق المتقادمة، الفروع المدمجة، السجلات القديمة، والوسائط/السجلات اليتيمة.
2. **Classify:** تصنيف كل عنصر إلى `KEEP` أو `ARCHIVE` أو `QUARANTINE` أو `DELETE_CANDIDATE` أو `MANUAL_REVIEW` مع سبب وبصمة.
3. **Prove:** تشغيل اختبارات المرجع، تحليل الاستدعاءات، وفحص الروابط والعقود قبل اعتبار العنصر غير مستخدم.
4. **Quarantine:** نقل العناصر القابلة للإزالة إلى مساحة مؤقتة أو Release manifest قابلة للاستعادة؛ لا حذف دائم في أول دورة.
5. **Purge:** الحذف النهائي فقط بعد مدة احتفاظ محددة، نجاح Restore Drill، وتطابق Exact-Head Evidence.

#### نطاق CleanGuard

- Git: الفروع المدمجة والمتقادمة، Worktrees المهجورة، ملفات Patch المؤقتة، وArtifacts غير المقصودة.
- Code: JavaScript/CSS/HTML غير المستدعى، مسارات Compatibility المتجاوزة، Fixtures ومختبرات Never-Merge.
- Documentation: الوثائق المتعارضة أو المستبدلة بعد نقلها إلى Archive وربط البديل الرسمي.
- Runtime: Cache versions القديمة وService Worker caches بصورة آمنة.
- Supabase Storage: Uploads غير المكتملة والوسائط اليتيمة بعد التحقق من عدم وجود Reference.
- Database: سجلات مؤقتة/منتهية وفق سياسة Retention مكتوبة، مع منع حذف Audit Ledger والسجلات القانونية.
- Logs: تقليل السجلات وفق Retention وPrivacy Policy، من دون إخفاء أدلة أمنية أو تشغيلية لازمة.

#### حواجز CleanGuard

- الوضع الافتراضي `DRY_RUN=true`.
- لا يتعامل مع Production عند غياب Backup حديث وRestore Drill ناجح.
- لا يحذف ملفات Canonical أو Migrations مطبقة أو عقود Authority أو Audit Records.
- أي التباس يؤدي إلى `MANUAL_REVIEW` وليس حذفًا.
- كل دورة تنتج JSON Manifest قابلًا للتدقيق يتضمن المسار، النوع، السبب، SHA/Hash، الإجراء، ونتيجة الاستعادة.

## 6. تصنيف الفروع وPull Requests

كل PR مفتوح يحصل على حالة واحدة فقط:

- `INTEGRATION_CANDIDATE`: شريحة لازمة، خضراء، وقابلة للاستخراج.
- `DOCS_AUTHORITY_CANDIDATE`: عقد أو مواصفة لازمة قبل التنفيذ.
- `VERIFICATION_ONLY`: مختبر CI يُغلق من دون دمج.
- `SUPERSEDED`: استبدلته سلطة أحدث.
- `LEGACY_REVIEW_REQUIRED`: يحتوي قيمة محتملة لكن معماريته قديمة.
- `CLOSE_NO_MERGE`: لا قيمة إنتاجية متبقية أو خطره أعلى من فائدته.
- `RELEASE_BLOCKED`: صحيح تقنيًا لكنه يحتاج اعتمادًا أو بيئة أو دليلًا إنتاجيًا.

السلسلة V13.1 لا تُدمج ككتلة واحدة. تُستخرج بحسب الترتيب المنطقي التالي بعد إعادة الاختبار على قاعدة نظيفة:

1. الدستور التنفيذي.
2. حساب عالمي وسياق دولة.
3. عقود التفويض ونطاق الدولة.
4. Migration محلية مراجعة.
5. Command Handler.
6. Command Boundary.
7. Query Pipeline.
8. Media Payload Foundation.
9. Zero-Trust Release Engine.

PRs التي تحمل `NEVER MERGE` تُغلق بعد حفظ دليل الاختبار ولا تدخل Integration Train.

## 7. بيئات التنفيذ

### Local

- Static server على `localhost`.
- Supabase محلي فقط عند اختبار Database.
- مفاتيح اختبار منفصلة وغير متتبعة.

### Preview

- نشر آلي لكل PR من Artifact مطابق للـSHA.
- بيانات اصطناعية فقط.
- لا صلاحيات إنتاجية.

### Staging

- Clerk وSupabase مستقلان عن Production.
- نفس Schema والسياسات والإعدادات القابلة للتكرار.
- اختبارات E2E وAccessibility وPerformance وSecurity كاملة.

### Production

- نشر Canary محدود.
- Migration Window مع Backup وRollback.
- مراقبة لحظية وKill Switch.
- توسيع تدريجي بعد ثبات مؤشرات القبول.

## 10. قواعد اتخاذ القرار بالتفويض

التفويض يسمح باتخاذ القرارات التالية دون إعادة سؤال المالك في كل خطوة:

- اختيار بنية الملفات الداخلية والأسماء التقنية.
- اختيار أسلوب الاختبار وأداة التحليل المناسبة.
- إغلاق PRs التجريبية الواضحة بعد حفظ الدليل.
- إنشاء فروع وCommits وPRs توثيقية وتنفيذية آمنة.
- إصلاح أخطاء الكود والاختبارات وCI ضمن العقود المعتمدة.
- تحسين UX والأداء والوصولية دون تغيير نموذج الأعمال.
- تنفيذ CleanGuard في Dry Run وQuarantine وإزالة المخلفات المثبتة بعد نجاح الاستعادة.

العمليات التالية تبقى محكومة ببوابة عملية لأنها تحتاج موارد خارج المستودع، لا لأنها تحتاج قرارًا تقنيًا جديدًا:

- تدوير مفتاح داخل حساب مزود خارجي عندما لا تكون صلاحية الحساب متاحة.
- شراء خدمة أو نطاق أو اشتراك.
- اعتماد نص قانوني نهائي لدولة محددة.
- تنفيذ Migration أو دفع أو نشر Production فعلي قبل اكتمال Staging وBackup وRollback.

عند غياب مورد خارجي، يستمر العمل في جميع الأجزاء القابلة للتنفيذ ولا يتوقف البرنامج كله.

## 11. معالجة الأخطاء والتراجع

- كل وحدة تُرجع Error Code ثابتًا ورسالة مستخدم غير كاشفة للتفاصيل الحساسة.
- لا Catch عام يحول الفشل إلى نجاح.
- كل Migration لها Rollback Review وBackup Evidence.
- كل Release لها Artifact SHA ونسخة سابقة قابلة للاستعادة.
- كل Feature كبيرة خلف Flag حتى اكتمال التحقق.
- فشل الهوية أو التفويض أو التخزين أو الدفع يوقف العملية ولا يترك نجاحًا جزئيًا.
- كل عملية CleanGuard لها Manifest وQuarantine/Restore path؛ الفشل في الإثبات يمنع Purge.

## 12. معايير اكتمال البرنامج

يُعد البرنامج مكتملًا عندما تتحقق جميع الشروط التالية:

1. لا أسرار متتبعة ولا مفاتيح إنتاجية في تاريخ الإصدار المستخدم.
2. مصدر حقيقة واحد دون تعليمات Auth أو Database متنافسة.
3. PR Registry يغطي جميع PRs المفتوحة ولا توجد سلسلة مجهولة الاعتماد.
4. المسارات الأساسية تعمل على Staging: الدخول، الحساب، الدولة، الإعلان، الصور، البحث، الملف، التواصل، الإدارة.
5. جميع عمليات السلطة خادمية ومغطاة بـRLS واختبارات سلبية.
6. Lighthouse/Accessibility/Browser/Mobile gates ضمن الحدود المحددة في خطط البرامج الفرعية.
7. Backup وRestore وRollback مجربة.
8. Production Canary ناجح بلا ارتفاع غير مقبول في الأخطاء.
9. وثائق التشغيل والحوادث محدثة ومطابقة للواقع.
10. Release Decision Engine يصدر `RELEASE_ELIGIBLE` على SHA المنشور نفسه.
11. CleanGuard يعمل دوريًا بوضع آمن ويثبت عدم وجود مخلفات عالية الخطورة أو حذف غير قابل للاستعادة.

## 13. القرار التنفيذي التالي

يبدأ التنفيذ بالبرنامج A: **Security Containment, Repository Consolidation and TIGER CleanGuard**، لأنه يقلل الخطر فورًا ويمنع البناء فوق مصدر حقيقة متناقض أو مخلفات مجهولة. بعد إغلاقه تنتقل البرامج B–G بترتيب الاعتماد، مع إمكانية تنفيذ أعمال UX غير المتعارضة بالتوازي على فروع مستقلة.
