# VVIP TIGER — مراجعة سيناريوهات أمان RPC المحسّن

## الملف محل المراجعة

`docs/security/sql-review/20260709_vvip_tiger_atomic_profile_resolver_rpc_hardened_review.sql`

## الحالة

`REVIEW_ONLY_NOT_APPLIED`

هذا الملف لم يتم تطبيقه على Supabase production.

## التصنيف الحالي

`READY_FOR_REPO_REVIEW_NOT_PRODUCTION_APPLY`

المعنى:
الملف مناسب للمراجعة داخل المستودع، لكنه غير معتمد للتطبيق على الإنتاج قبل backup ومراجعة يدوية نهائية.

---

## السيناريو 1 — مستخدم مسجل ولديه profile مربوط سابقًا

### الحالة

- المستخدم authenticated.
- يوجد `clerk_user_id` داخل JWT.
- يوجد صف في `public.profiles` بنفس `clerk_user_id`.

### السلوك المتوقع

- تحميل profile مباشرة.
- لا يتم إنشاء صف جديد.
- لا يتم تعديل صف قديم.
- يرجع JSON آمن فقط.

### الحكم

آمن.

---

## السيناريو 2 — مستخدم Clerk لديه profile قديم بنفس البريد وبدون clerk_user_id

### الحالة

- المستخدم authenticated.
- يوجد `sub` داخل JWT.
- يوجد بريد موثق داخل JWT.
- يوجد profile قديم بنفس البريد.
- `clerk_user_id` في profile فارغ أو null.

### السلوك المتوقع

- يتم ربط profile القديم بـ Clerk user id.
- يتم التحديث فقط إذا البريد جاء من JWT.
- لا يتم الاعتماد على `p_email`.

### الحكم

آمن بشرط أن يكون البريد الموجود في JWT موثوقًا من Clerk.

---

## السيناريو 3 — مستخدم يرسل p_email لبريد شخص آخر

### الحالة

- المستخدم authenticated.
- يحاول تمرير بريد شخص آخر عبر `p_email`.

### السلوك المتوقع

- `p_email` لا يستخدم لإثبات الملكية.
- لا يتم claim لأي profile بناءً على `p_email`.
- إذا لا يوجد بريد داخل JWT، يرجع status آمن ولا ينشئ profile.

### الحكم

الخطر مغلق في النسخة المحسّنة.

---

## السيناريو 4 — مستخدم بدون بريد موثق داخل JWT

### الحالة

- المستخدم authenticated.
- يوجد `sub`.
- لا يوجد email موثوق داخل JWT.
- قد يرسل المستخدم `p_email`.

### السلوك المتوقع

- لا يتم إنشاء profile.
- لا يتم استرجاع profile قديم.
- يظهر status آمن:
  `missing_verified_email`

### الحكم

آمن.

---

## السيناريو 5 — محاولة update مباشر على public.profiles

### الحالة

- مستخدم authenticated يحاول تعديل صفه مباشرة عبر API.

### السلوك المتوقع

- direct insert/update/delete revoked من authenticated.
- التحديثات الحساسة لا تتم مباشرة من الجدول.
- أي تعديل مستقبلي يجب أن يتم عبر RPC مخصصة ومحدودة.

### الحكم

تحسن أمني مهم.

---

## السيناريو 6 — محاولة delete مباشر

### الحالة

- مستخدم authenticated أو anon يحاول حذف profile.

### السلوك المتوقع

- delete غير ممنوح.
- لا توجد policy delete.
- لا يوجد مسار delete داخل الدالة.

### الحكم

آمن.

---

## السيناريو 7 — unique conflict أثناء إنشاء profile

### الحالة

- يحدث تعارض unique أثناء insert.

### السلوك المتوقع

- الدالة تحاول تحميل profile بنفس `clerk_user_id`.
- إذا وجدته، تعيده بشكل آمن.
- إذا لم تجده، ترجع رسالة Tiger Care آمنة.

### الحكم

آمن من ناحية تجربة المستخدم، ويحتاج متابعة إدارية عند conflict غير محلول.

---

## السيناريو 8 — anon access

### الحالة

- مستخدم غير مسجل يحاول تنفيذ RPC.

### السلوك المتوقع

- execute مسحوب من anon.
- الدالة تتحقق أيضًا من `auth.role()`.

### الحكم

آمن.

---

## السيناريو 9 — خطأ غير متوقع داخل الدالة

### الحالة

- خطأ قاعدة بيانات غير متوقع.

### السلوك المتوقع

- لا يتم إرجاع خطأ raw للمستخدم.
- ترجع رسالة آمنة:
  `profile_resolver_safe_failure`

### الحكم

جيد لتجربة المستخدم، لكن يجب تسجيل الأخطاء لاحقًا في backend/admin logs عند توفر نظام logging.

---

## السيناريو 10 — إرجاع بيانات profile

### الحالة

- الدالة تعيد profile للمستخدم.

### السلوك المتوقع

- لا تستخدم `to_jsonb(v_profile)`.
- تعيد JSON محدد الأعمدة فقط.
- لا تكشف tokens أو secrets.
- لا تكشف role أو صلاحيات إدارية.

### الحكم

آمن مبدئيًا.

---

## ملاحظات لا تزال تحتاج مراجعة قبل الإنتاج

1. يجب عمل backup قبل أي تطبيق يدوي على Supabase.
2. يجب مراجعة الأعمدة الموجودة فعليًا في `public.profiles`.
3. يجب التأكد أن Clerk JWT يحتوي email موثوق في بيئة الإنتاج.
4. يجب اختبار RPC في Supabase SQL Editor على مستخدم تجريبي فقط.
5. يجب عدم تطبيق الملف مباشرة حتى يتم دمجه ومراجعته نهائيًا.
6. يجب لاحقًا بناء frontend fallback UX بحيث لا يشعر المستخدم بأي خلل.

## القرار

النسخة المحسّنة تعالج مخاطر النسخة السابقة داخل المستودع.

لكن القرار النهائي ليس تطبيقها الآن.

الحالة النهائية:

`REPO_REVIEW_READY`

وليست:

`PRODUCTION_READY`

## الخطوة التالية

بعد هذه الوثيقة، الخطوة القادمة تكون:

1. مراجعة نهائية للفرق بين migration القديم والمحسّن.
2. ثم فتح Pull Request.
3. ثم بعد الدمج فقط ننتقل إلى خطة backup + manual Supabase apply.

---

## قرار تنظيمي إضافي

تم نقل ملف SQL المحسّن إلى مجلد مراجعة آمن خارج `supabase/migrations`.

السبب:
ملفات `REVIEW ONLY` لا يجب أن تبقى داخل مجلد migrations الرسمي حتى لا يتم تطبيقها بالغلط مستقبلًا.

المسار الحالي الآمن:

`docs/security/sql-review/20260709_vvip_tiger_atomic_profile_resolver_rpc_hardened_review.sql`

عند اعتماد التطبيق لاحقًا، يتم إنشاء migration رسمي جديد داخل `supabase/migrations` بعد backup ومراجعة نهائية.
