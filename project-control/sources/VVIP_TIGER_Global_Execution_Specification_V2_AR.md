# 1. الملخص التنفيذي وتعريف النهاية العالمية

الهدف النهائي هو إطلاق VVIP TIGER كمنصة عالمية واحدة تعمل من خلال نواة برمجية موحدة وقابلة للتهيئة حسب الدولة واللغة والعملة، مع سوق إعلانات متعدد القطاعات، ملفات شخصية، تواصل فردي، دعم ومراجعة، اشتراكات، إدارة عالمية، وبنية أمنية وتشغيلية قابلة للتوسع. لا تتعامل Global V1 بأموال الصفقات بين المستخدمين، بل تبيع اشتراكات وخدمات ترويجية للمنصة فقط.

## 1.1 تعريف 100% من Global V1

- المستخدم يستطيع التسجيل والدخول وإكمال ملفه من أي دولة مفعلة وباللغة المدعومة.

- المستخدم يستطيع إنشاء إعلان بعملة وموقع وحقول مناسبة لقطاعه ودولته، ورفعه للمراجعة ونشره وإدارته.

- الإعلانات المنشورة تظهر في البحث والـFeed، وتعمل روابطها على الهاتف والكمبيوتر.

- التواصل فردي وآمن، والإشعارات تصل داخل المنصة وبالبريد وPush بحسب إعدادات المستخدم.

- توجد آليات بلاغ واستئناف ودعم Tiger Care وسجل إداري قابل للتدقيق.

- الاشتراكات والدفع تعمل عبر Hosted Checkout دون تخزين بيانات البطاقة في المنصة.

- توجد سياسات خصوصية وحذف وتصدير بيانات واحتفاظ حسب المناطق القانونية المستهدفة.

- تنجح اختبارات الأمان والأداء والاستعادة والدفع والصلاحيات ولا توجد ثغرة حرجة مفتوحة.

- يعمل الإطلاق العالمي العام عبر Capability Matrix مع إمكانية إيقاف دولة أو ميزة أو الدفع فورًا.

- توجد مراقبة وتشغيل واستجابة للحوادث ونسخ احتياطي واستعادة موثقة بعد الإطلاق.

# 2. الحالة الحالية والفجوات

هذه الوثيقة تفترض الاستفادة من التصميمات والملفات الحالية، لكنها لا تعتبرها مكتملة إلا بعد التحقق في المستودع وStaging. الأولوية هي إنهاء P08 أمنيًا، ثم دمج نظام الهوية الموحد P09 على دفعات صغيرة، ثم بناء المسار الإنتاجي الرأسي.

| المجال | ما يحتفظ به | ما يحتاج الإكمال | قرار التنفيذ |
| --- | --- | --- | --- |
| الهوية | Clerk وواجهة الدخول الحالية | توحيد Runtime وربط Supabase وMFA للإدارة | إصلاح ودمج تدريجي |
| التصميم | نظام التصميم ورحلات UX | ربط Backend وحالات الخطأ والفراغ والوصول | إعادة استخدام لا إعادة تصميم |
| قاعدة البيانات | تصميم P07 | migrations حقيقية وRLS وفهارس وRetention | إغلاق P08 قبل بيانات حقيقية |
| الإعلانات | واجهات ونماذج رحلة | محرك حالات وحقول ديناميكية وAPI ومراجعة | بناء وحدة إنتاجية واحدة |
| الإدارة | نماذج لوحات | RBAC وAudit وعمليات حقيقية | ربط تدريجي |
| الوثائق | حوكمة قوية | مواصفات تقنية وجداول تشغيل | تحديث مستمر من الكود |

# 3. المبادئ المعمارية العالمية

| المكوّن | القرار المعتمد |
| --- | --- |
| نمط التطبيق | Modular Monolith منظم إلى وحدات Domains؛ يمنع تعقيد Microservices المبكر. |
| الواجهة | تطبيق ويب Responsive وPWA أولًا، مع Design System وi18n مركزي. |
| الهوية | Clerk هو مصدر الهوية والجلسات؛ Supabase يحتفظ بالملف والصلاحيات والبيانات التطبيقية. |
| البيانات | PostgreSQL/Supabase مع migrations قابلة للتكرار، RLS افتراضيًا، وفهارس مبنية على الاستعلامات. |
| الملفات | Storage خاص/عام وفق Bucket Policies، معالجة صور غير متزامنة وCDN. |
| الخدمات الخلفية | Server-side API/Edge Functions للعمليات الحساسة، Webhooks موقعة، Queues للمهام البطيئة. |
| الدفع | Hosted Checkout ومزود عالمي؛ لا تخزين لأرقام البطاقات ولا Escrow في V1. |
| التوسع | منطقة بيانات أساسية + CDN عالمي، ثم توسع متعدد المناطق عند مؤشرات فعلية. |
| الأمان | Fail Closed، أقل صلاحية، Audit للأحداث الحساسة، Secret Manager، MFA للأدوار الإدارية. |
| الإطلاق | Feature Flags وCountry Capability Matrix وRollback آلي وموجات Beta. |

## 10.1 قواعد API الملزمة

- JSON schema موثق لكل request/response.

- Error envelope موحد: code, message_key, field_errors, correlation_id.

- Idempotency-Key للعمليات المالية والإرسال والإنشاء القابل للتكرار.

- Rate limits حسب الهوية والجهاز والعنوان والعملية.

- Audit event للأفعال الإدارية والمالية والحذف.

- Versioning تحت /api/v1 وتوافق خلفي خلال نافذة الإصدار.

# 11. حالات الإعلانات والمحادثات والدفع

## 11.1 State Machine للإعلان

| من | إلى | المنفذ | الشرط |

| pending_review | rejected | المراجع | سبب رفض موحد |

| published | paused | المالك/الإدارة | توقف مؤقت |
| paused | published | المالك/الإدارة | الباقة والمدة ساريتان |
| published | expired | النظام | بلوغ تاريخ الانتهاء |
| expired | published | المالك | تجديد ناجح |
| published | sold | المالك | إغلاق طوعي |
| أي حالة | removed | الإدارة | مخالفة/طلب قانوني |
| draft/rejected/expired/sold | archived | المالك/النظام | وفق سياسة الاحتفاظ |

## 11.2 قواعد المحادثة

- طرفان فقط في V1؛ لا مجموعات ولا Broadcast.

- يمكن اعتماد محادثة واحدة لكل (listing, buyer, seller) لمنع التكرار.

- client_message_id فريد لكل مرسل لمنع حفظ الرسالة مرتين.

- الحظر يمنع الرسائل الجديدة ولا يحذف الدليل السابق تلقائيًا.

- حذف الحساب يتبع سياسة الاحتفاظ والالتزامات القانونية؛ لا يمحو Evidence بلا مراجعة.

- المرفقات تبدأ بالصور فقط أو تؤجل؛ الملفات العامة تحتاج فحصًا منفصلًا.

# 17. قائمة الإطلاق والتسليم النهائي

- Global V1 contract موقع ولا توجد P0 requirements بلا مالك.

- main محمي وCI أخضر وProduction deploy approval مفعل.

- Clerk/Supabase reconciliation = صفر أخطاء غير معالجة.

- كل جداول التطبيق RLS ومغطاة باختبارات إيجابية وسلبية.

- Backup restore drill ناجح ضمن RTO/RPO.

- المسارات: التسجيل، الإعلان، البحث، الرسائل، البلاغ، الدعم، الدفع تمر E2E.

- لا Critical/Blocker مفتوح، وHigh المقبولة موثقة ومحدودة.

- Country capability/legal/payment matrix معتمدة لكل دولة مفتوحة.

- سياسات الخصوصية والشروط والاسترجاع والمحتوى منشورة بالإصدارات الصحيحة.

- فريق الدعم والمراجعة وon-call جاهز وجداول التصعيد مختبرة.

- Dashboards وalerts وstatus communication جاهزة.

- Kill switches وrollback وread-only mode مختبرة.

- Closed Beta وPublic Beta استوفت مؤشرات الانتقال.

- قرار Go/No-Go موقع من Owner وTech وSecurity وQA وOperations.

# الخلاصة وقرار التنفيذ

يمكن تنفيذ VVIP TIGER كمنصة عالمية حقيقية دون إعادة البناء الكامل، بشرط اعتماد هذه المواصفة كمرجع، إغلاق الهوية وP08 أمنيًا أولًا، ثم بناء مسار الإعلان والبحث والتواصل والدفع على نواة عالمية قابلة للتهيئة. أسرع مدة مسؤولة بفريق 7–9 متخصصين هي 8–10 أشهر إلى Global V1، بينما يقل الفريق أو تأخر القرارات يرفع المدة. لا يجوز اعتبار المشروع 100% قبل اجتياز قائمة الإطلاق والتشغيل الفعلي بالموجات.
